4.1 Introduction à SPARQL

Le langage qui interroge les graphes de connaissances.

SPARQL en une phrase

SPARQL Protocol And RDF Query Language
un acronyme récursif, comme SQL l'inspire.

Le langage standard du W3C pour interroger n'importe quel graphe RDF, qu'il fasse dix triplets ou dix milliards.

Vous avez déjà vu SPARQL, sans le savoir

Cette requête, montrée au chapitre 1, croisait les finales de Coupe du Monde FIFA et les chefs de gouvernement en poste. C'était déjà du SPARQL, sur Wikidata.

Ce chapitre apprend à lire, puis à écrire, exactement ce genre de requête.

Historique

SPARQL 1.0Première recommandation W3C, en 2008. Pose les bases du langage.
SPARQL 1.1Recommandation W3C en 2013, nettement plus riche. Les nouveautés seront introduites au fil de ce chapitre.
SPARQL 1.2Une nouvelle version, en cours de conception au W3C au moment de ce cours.
Langage + protocoleSPARQL n'est pas qu'une syntaxe de requête : c'est aussi un protocole HTTP standardisé, qui permet d'interroger un graphe distant via une simple URL.

Une syntaxe familière

Sélectionner les joueurs espagnols, en SQL puis en SPARQL.

SQL

SELECT nom
FROM Joueurs
WHERE nationalite = 'Espagne';

SPARQL

SELECT ?nom
WHERE {
  ?joueur ex:nom ?nom ;
          ex:nationalite "Espagne"@fr .
}

La vraie différence : tables contre motifs

SQLFiltre des lignes dans des tables à schéma fixe. Les jointures suivent des clés étrangères déclarées à l'avance.
SPARQLFiltre des motifs de triplets dans un graphe sans schéma préétabli. Les jointures se font en réutilisant la même variable, sans rien déclarer.

Le principe : le pattern matching

Une requête SPARQL est elle-même un petit graphe, avec des trous : les variables.
On cherche toutes les façons de le faire correspondre au graphe de données.

Motif de la requête
?joueur ex:nationalite "Espagne"
→
Graphe de données
ex:alcaraz ex:nationalite "Espagne"
ex:sinner ex:nationalite "Italie"

Une seule correspondance : ?joueur se lie à ex:alcaraz.

Les quatre formes de requêtes

FormeRésultat
SELECTUne table de résultats (comme SQL)
CONSTRUCTUn nouveau graphe RDF
ASKUn booléen : vrai ou faux
DESCRIBEUne description d'une ressource

SELECT pour explorer, CONSTRUCT pour matérialiser, ASK pour vérifier, DESCRIBE pour documenter.

La forme de base d'une requête SELECT

SPARQL 
PREFIX ex: <http://example.org/>

SELECT ?nom
WHERE {
  ?joueur ex:nom ?nom .
}

→ PREFIX déclare les abréviations, SELECT choisit les variables à afficher, WHERE contient les motifs à faire correspondre.

Une première requête

Sur un petit extrait du graphe Roland-Garros que nous allons poser en entier dans la prochaine section :

ex:alcaraz  ex:nom "Carlos Alcaraz" ; ex:nationalite "Espagne" .
ex:sinner   ex:nom "Jannik Sinner"  ; ex:nationalite "Italie" .
SPARQL 
SELECT ?nom WHERE {
  ?joueur ex:nom ?nom ;
          ex:nationalite "Espagne" .
}
?nom = "Carlos Alcaraz"

4.2 Filtrer et combiner : les graph patterns

Le même graphe, interrogé de plus en plus finement.

Le graphe complet

Roland-Garros 2024, cinq joueurs et trois matchs. Toutes les requêtes suivantes interrogent ce même graphe.

Turtle 
ex:alcaraz  a ex:Joueur ; ex:nom "Carlos Alcaraz" ; ex:nationalite "Espagne" ; ex:classementATP 2 .
ex:sinner   a ex:Joueur ; ex:nom "Jannik Sinner" ; ex:nationalite "Italie" ; ex:classementATP 3 .
ex:zverev   a ex:Joueur ; ex:nom "Alexander Zverev" ; ex:nationalite "Allemagne" ; ex:classementATP 6 .
ex:ruud     a ex:Joueur ; ex:nom "Casper Ruud" ; ex:nationalite "Norvège" .
ex:djokovic a ex:Joueur ; ex:nom "Novak Djokovic" ; ex:nationalite "Serbie" ; ex:classementATP 1 .

ex:rg2024_demi1  a ex:Match ; ex:tour "Demi-finale" ; ex:joueur1 ex:alcaraz ; ex:joueur2 ex:sinner ; ex:vainqueur ex:alcaraz .
ex:rg2024_demi2  a ex:Match ; ex:tour "Demi-finale" ; ex:joueur1 ex:zverev  ; ex:joueur2 ex:ruud   ; ex:vainqueur ex:zverev .
ex:rg2024_finale a ex:Match ; ex:tour "Finale"       ; ex:joueur1 ex:alcaraz ; ex:joueur2 ex:zverev ; ex:vainqueur ex:alcaraz .

→ Remarquez : ex:ruud n'a pas de ex:classementATP. Un graphe réel est rarement complet.

Le même graphe, en schéma

Plus facile à suivre visuellement quand on cherche un pattern dans les diapositives suivantes.

Un pattern = une ligne de la clause WHERE

Un pattern est un triplet où n'importe quelle position, sujet, prédicat ou objet, peut être remplacée par une variable (préfixée par ?).

SPARQL 
?joueur ex:nationalite "Italie" .

→ Trouve toutes les valeurs de ?joueur reliées à "Italie" par ex:nationalite.

Plusieurs patterns : une jointure implicite

Deux patterns qui partagent la même variable se joignent automatiquement, sans JOIN ON à écrire.

SPARQL 
SELECT ?nomVainqueur WHERE {
  ?match ex:tour "Finale" ;
         ex:vainqueur ?vainqueur .
  ?vainqueur ex:nom ?nomVainqueur .
}

→ ?match relie les deux premiers patterns, ?vainqueur relie le deuxième au troisième.

À vous : devinez le résultat

SPARQL 
SELECT ?nom WHERE {
  ?match ex:tour "Demi-finale" ;
         ex:vainqueur ?vainqueur .
  ?vainqueur ex:nom ?nom .
}

Le graphe a deux demi-finales. Combien de résultats ?

"Carlos Alcaraz" et "Alexander Zverev"

FILTER : une condition sur une variable

Un pattern seul ne peut exprimer que de l'égalité. FILTER ajoute des conditions numériques, textuelles ou logiques.

SPARQL 
SELECT ?nom WHERE {
  ?joueur ex:nom ?nom ;
          ex:classementATP ?rang .
  FILTER(?rang < 5)
}

→ Ne garde que les joueurs classés dans les 5 premiers mondiaux.

OPTIONAL : ne pas perdre une ligne

ex:ruud n'a pas de ex:classementATP. Un pattern normal l'exclurait entièrement du résultat.

SPARQL 
SELECT ?nom ?rang WHERE {
  ?joueur ex:nom ?nom .
  OPTIONAL { ?joueur ex:classementATP ?rang . }
}

→ Casper Ruud apparaît quand même dans le résultat, avec ?rang non liée.

Le piège : filtrer une variable optionnelle

SPARQL 
SELECT ?nom ?rang WHERE {
  ?joueur ex:nom ?nom .
  OPTIONAL { ?joueur ex:classementATP ?rang . }
  FILTER(?rang < 10)
}

↛ Pour Casper Ruud, ?rang n'est pas liée : le FILTER échoue silencieusement et la ligne disparaît, comme si OPTIONAL n'avait servi à rien.

UNION : deux motifs alternatifs

Trouver les joueurs présents en finale, comme vainqueur ou comme adversaire.

SPARQL 
SELECT ?nom WHERE {
  ?match ex:tour "Finale" .
  { ?match ex:vainqueur ?j . }
  UNION
  { ?match ex:joueur2 ?j . }
  ?j ex:nom ?nom .
}

→ Résultat : Carlos Alcaraz (vainqueur) et Alexander Zverev (adversaire), sans doublon.

MINUS contre OPTIONAL

Une confusion classique : les deux ressemblent à un filtre négatif, mais ne font pas la même chose.

OPTIONAL

Garde toutes les lignes. Si le motif ne correspond pas, la variable reste simplement non liée.

MINUS

Exclut carrément la ligne si le motif correspond. Sert à écarter des résultats, jamais à les enrichir.

ORDER BY et LIMIT

Trier les joueurs classés par rang ATP croissant, ne garder que le podium.

SPARQL 
SELECT ?nom ?rang WHERE {
  ?joueur ex:nom ?nom ;
          ex:classementATP ?rang .
}
ORDER BY ?rang
LIMIT 3

→ Djokovic (1), Alcaraz (2), Sinner (3).

Le piège : trier sans limiter

ORDER BY sans LIMIT doit trier tout le résultat avant de répondre.

Sur notre graphe de cinq joueurs, aucun souci. Sur un endpoint public comme Wikidata, avec des millions de résultats potentiels, la même requête peut simplement expirer (timeout) avant de renvoyer quoi que ce soit.

Toujours ajouter LIMIT en phase d'exploration d'un grand graphe.

4.3 Agréger et construire

Résumer un graphe en chiffres, ou en fabriquer un nouveau.

COUNT et GROUP BY

Compter les matchs par tour du tournoi.

SPARQL 
SELECT ?tour (COUNT(?match) AS ?nb) WHERE {
  ?match ex:tour ?tour .
}
GROUP BY ?tour
"Demi-finale" → 2  ·  "Finale" → 1

DISTINCT : éliminer les doublons

Carlos Alcaraz apparaît dans deux matchs comme ex:joueur1. Sans DISTINCT, son nom sortirait deux fois.

SPARQL 
SELECT DISTINCT ?nom WHERE {
  ?match ex:joueur1 ?j .
  ?j ex:nom ?nom .
}

→ "Carlos Alcaraz" n'apparaît qu'une seule fois, malgré ses deux matchs.

Les autres agrégats

AVGMoyenne d'une valeur numérique.
MIN / MAXValeur minimale ou maximale.
SUMSomme d'une valeur numérique.
SPARQL 
SELECT (AVG(?rang) AS ?rangMoyen) WHERE {
  ?joueur ex:classementATP ?rang .
}

CONSTRUCT en pratique

Fabriquer un raccourci ex:aBattu à partir des matchs. Comme le raisonnement du chapitre 3, mais déclenché par une requête plutôt que par un raisonneur.

SPARQL 
CONSTRUCT { ?vainqueur ex:aBattu ?perdant . }
WHERE {
  ?match ex:vainqueur ?vainqueur ;
         ex:joueur1 ?j1 ; ex:joueur2 ?j2 .
  BIND(IF(?vainqueur = ?j1, ?j2, ?j1) AS ?perdant)
}

→ BIND calcule "l'autre joueur". Le résultat est un nouveau graphe RDF, pas une table.

ASK en pratique

"Casper Ruud a-t-il un classement ATP renseigné dans notre graphe ?"

SPARQL 
ASK {
  ex:ruud ex:classementATP ?rang .
}
false

→ Un booléen, pas une table : idéal pour une simple vérification.

4.4 Triplestores, endpoints et fédération

Où vivent les graphes que l'on interroge.

Qu'est-ce qu'un triplestore ?

DéfinitionUn moteur de base de données spécialisé dans le stockage et l'interrogation de graphes RDF.
IndexationIndex sur les permutations de sujet, prédicat, objet (SPO, POS, OSP...), pour retrouver n'importe quel pattern rapidement.
Différence avec SQLUn SGBD relationnel (section 2.1) organise des tables à schéma fixe. Un triplestore organise un seul grand graphe, sans schéma préétabli.

Des triplestores réels

TriplestoreUtilisé par
VirtuosoDBpedia, UniProt
BlazegraphWikidata (historiquement)
Apache Jena FusekiProjets open source, prototypage
GraphDB (Ontotext)Le triplestore de ce cours

Le endpoint SPARQL

Un triplestore expose son graphe via une URL HTTP qui accepte des requêtes SPARQL : le endpoint. C'est le "SPARQL Protocol", la deuxième moitié du standard, à côté du langage lui-même.

https://query.wikidata.org/sparql

C'est exactement cet endpoint que la démo FIFA du chapitre 1 interrogeait.

La fédération : interroger plusieurs endpoints

La clause SERVICE délègue une partie du motif à un endpoint distant, et combine le résultat avec le reste de la requête locale.

SPARQL 
SELECT ?nom ?paysWikidata WHERE {
  ex:alcaraz ex:nom ?nom .
  SERVICE <https://query.wikidata.org/sparql> {
    wd:Q85518537 wdt:P27 ?paysWikidata .
  }
}

→ Une partie locale, une partie distante, une seule requête. Le même principe que la démo FIFA du chapitre 1.

Le piège de la fédération

Chaque bloc SERVICE est un aller-retour HTTP séparé vers un serveur distant.

Un endpoint distant lent, surchargé ou indisponible ralentit ou fait échouer la requête entière, même si le reste des données est disponible localement. À la différence d'une jointure locale, la latence réseau devient une variable du problème.

GraphDB : le triplestore de ce cours

Les travaux pratiques de ce module utilisent GraphDB (Ontotext) : un triplestore avec son propre endpoint SPARQL, et surtout OntoRefine intégré pour construire un graphe depuis un tableur, sujet du chapitre 5.

Synthèse : SPARQL (1/2)

SPARQL interroge un graphe par filtrage de motifs de triplets (pattern matching), pas par jointure de tables à schéma fixe. Les variables partagées font office de jointure.

Quatre formes de requête : SELECT (table), CONSTRUCT (nouveau graphe), ASK (booléen), DESCRIBE (description d'une ressource).

FILTER ajoute des conditions, OPTIONAL garde une ligne même sans correspondance, UNION combine des motifs alternatifs, MINUS exclut plutôt qu'il n'enrichit.

Synthèse : SPARQL (2/2)

GROUP BY et les agrégats (COUNT, AVG...) résument un graphe en chiffres. ORDER BY sans LIMIT reste un piège sur un grand graphe.

Un triplestore stocke le graphe, un endpoint l'expose en HTTP, la fédération (SERVICE) combine plusieurs endpoints en une seule requête. Ce cours utilise GraphDB.

RDF décrit, RDFS/OWL déduisent, SPARQL interroge. Reste à voir comment construire un graphe à partir de données existantes : c'est l'objet du chapitre suivant.
